# Hinata Documentation

The official documentation & self-hosting guide for **[Hinata](https://github.com/hinata-platform)** —
an open-source, self-hosted project & issue tracker with one published client app for self-hosted server instances.

📖 **Live site: https://hinata.ahmadre.com**

The docs are bilingual (English 🇬🇧 / Deutsch 🇩🇪) and cover every feature plus a
complete guide to running your own server and shipping your own branded client.

- **App:** https://github.com/hinata-platform/hinata-app
- **Server:** https://github.com/hinata-platform/hinata-server

---

## How it's built

A **Next.js** app (App Router, React 19, Turbopack) with `output: 'export'`:
every route is pre-rendered to static HTML at build time, so GitHub Pages
serves files and there is no server anywhere. 108 documentation pages — 54 in
each language — plus the landing page, the search index and the sitemap.

Markdown from `content/<lang>/*.md` goes through a remark/rehype pipeline with
build-time Shiki highlighting. The Liquid-Glass theme is one stylesheet,
`app/globals.css`.

```
content/
  nav.json          # navigation & site structure (single source of truth)
  en/*.md           # English pages
  de/*.md           # German pages
app/
  page.tsx          # the landing page (one URL, both languages)
  [lang]/[slug]/    # every documentation page
  globals.css       # the whole theme
  sitemap.ts · robots.ts · search-index.json/route.ts
components/         # the chrome — top bar, sidebar, ⌘K palette, TOC rail
lib/
  markdown.ts       # remark/rehype: admonitions, <picture>, Shiki, headings
  content.ts        # the nav model; source.ts and images.ts read from disk
  version.ts        # the platform version, resolved from the newest app tag
assets/             # favicon and the screenshots (masters + optimized variants)
scripts/            # asset mirror and legacy-URL stubs, run around the build
tools/              # the screenshot optimizer and the capture pipeline
public/             # generated by scripts/sync-assets.mjs — do not edit
```

### Requirements

Node 24, which is what CI builds with. Nothing else; the Python here is for the
screenshot tooling only.

### Build locally

```bash
npm install
npm run dev                        # http://localhost:3000
npm run build && npm run preview   # the real export, served from out/
```

`npm run build` is three steps: mirror `assets/` into `public/` (minus the
71 MB of master PNGs nothing links to any more), export with Next, then write
the stubs that keep the old `.html` URLs answering.

> **A local build calls the GitHub API.** The platform version shown on the
> site is the newest `vX.Y.Z` tag on hinata-app, resolved while building, and a
> failure aborts the build rather than inventing a number. Anonymous calls are
> capped at 60/h per IP, so export `GITHUB_TOKEN` if you build often. CI passes
> its own. Between deploys the browser refreshes the number itself, so a
> release that ships after the last build is still shown correctly.

### Screenshots

Screenshots are not served as authored. `tools/optimize_images.py` writes AVIF
and WebP at up to four widths (480 / 960 / 1440 / 1920, never wider than the
master) plus a 48px blur-up placeholder, and records them in a manifest the
markdown pipeline reads to emit a `<picture>` with the right `srcset` and the
image's intrinsic size.

```bash
npm run images     # after adding or replacing a screenshot; needs Python + Pillow
```

Its output is committed — the encode is slow enough that doing it in CI would
add minutes to every deploy, and the results are deterministic. Two rules the
pipeline enforces, both learned the hard way: the placeholder never goes behind
an image with transparency (a background under a cut-out never goes away), and
`srcset` only ever offers widths that exist.

### URLs

Pages live at `/<lang>/<slug>/`, the landing page at `/`. Two language-neutral
entry points, `/privacy-policy` and `/terms-of-service`, forward to the
reader's language — those are the addresses the apps and the store listings
point at, so they cannot move.

The generator this replaced wrote `/<lang>/<slug>.html`. Those addresses are in
the store listings, in the apps and in other people's links, so every one of
them is still answered by a stub that redirects and declares the canonical —
`scripts/legacy-urls.mjs` writes them after the export.

### Deploy

Every push to `main` triggers `.github/workflows/deploy.yml`, which builds the
site and publishes it to GitHub Pages. No manual step required. It also runs
weekly, and hinata-app can trigger it on release with a `repository_dispatch`
of type `app-release`, so the version on the site keeps up with the app.

## Contributing to the docs

1. Edit or add a Markdown file under `content/en/` **and** `content/de/`
   (both languages are required).
2. If you add a page, register its slug + titles in `content/nav.json`.
3. Follow the conventions in [`tools/AUTHORING_BRIEF.md`](tools/AUTHORING_BRIEF.md).
4. Open a pull request.

Two things about the Markdown dialect, both inherited from the generator this
replaced and both supported deliberately: admonitions are written
`!!! note "Title"` with a four-space-indented body, and the `---` front matter
splits on the first colon, so a description may contain one unquoted.
