# Hinata Documentation

The documentation and self-hosting guide for **[Hinata](https://github.com/hinata-platform)**,
an open-source project and issue tracker you run on your own server.

📖 **Live site: https://hinata.ahmadre.com**

The docs are in English 🇬🇧 and German 🇩🇪. They cover every feature, running
your own server and building your own branded app.

- **App:** https://github.com/hinata-platform/hinata-app
- **Server:** https://github.com/hinata-platform/hinata-server

---

## How it's built

A **Next.js** app (App Router, React 19, Turbopack) with `output: 'export'`.
Every route is rendered to static HTML at build time, so GitHub Pages only
serves files. That makes 108 documentation pages (54 per language), plus the
landing page, the search index and the sitemap.

Markdown from `content/<lang>/*.md` runs through a remark/rehype pipeline with
Shiki highlighting at build time. The Liquid Glass theme is one stylesheet,
`app/globals.css`.

```
content/
  nav.json          # navigation & site structure (single source of truth)
  en/*.md           # English pages
  de/*.md           # German pages
app/
  page.tsx          # the landing page (one URL, both languages)
  [lang]/[slug]/    # every documentation page
  globals.css       # the whole theme
  sitemap.ts · robots.ts · search-index.json/route.ts
components/         # top bar, sidebar, ⌘K palette, TOC rail
lib/
  markdown.ts       # remark/rehype: admonitions, <picture>, Shiki, headings
  content.ts        # the nav model; source.ts and images.ts read from disk
  version.ts        # the platform version, resolved from the newest app tag
assets/             # favicon and the screenshots (masters + optimized variants)
scripts/            # asset mirror and legacy URL stubs, run around the build
tools/              # the screenshot optimizer and the capture pipeline
public/             # generated by scripts/sync-assets.mjs, do not edit
```

### Requirements

Node 24, the same as CI. The Python here is only for the screenshot tooling.

### Build locally

```bash
npm install
npm run dev                        # http://localhost:3000
npm run build && npm run preview   # the real export, served from out/
```

`npm run build` does three things: copy `assets/` into `public/` (without the
71 MB of master PNGs), export with Next, and write the stubs for the old `.html`
URLs.

> **A local build calls the GitHub API.** The version shown on the site is the
> newest `vX.Y.Z` tag on hinata-app. If the lookup fails, the build fails.
> Anonymous calls are limited to 60 per hour per IP, so export `GITHUB_TOKEN` if
> you build often. CI uses its own token. The browser also refreshes the version,
> so a release after the last build still shows up.

### Screenshots

`tools/optimize_images.py` writes AVIF and WebP in up to four widths
(480 / 960 / 1440 / 1920, never wider than the master) plus a 48px blur
placeholder. It records them in a manifest, and the markdown pipeline uses that
to emit a `<picture>` with the right `srcset` and size.

```bash
npm run images     # after adding or replacing a screenshot; needs Python + Pillow
```

The output is committed. Encoding in CI would add minutes to every deploy, and
the result is always the same. Two rules apply: images with transparency get no
placeholder behind them, and `srcset` only lists widths that exist.

### URLs

Pages live at `/<lang>/<slug>/`, the landing page at `/`. `/privacy-policy` and
`/terms-of-service` forward to the reader's language. The apps and store listings
link there, so these URLs must not change.

The old generator wrote `/<lang>/<slug>.html`. Those URLs still appear in store
listings, apps and other people's links. `scripts/legacy-urls.mjs` writes a stub
for each one after the export that redirects and sets the canonical URL.

### Deploy

Every push to `main` runs `.github/workflows/deploy.yml`, which builds the site
and publishes it to GitHub Pages. It also runs weekly, and hinata-app triggers it
on release with a `repository_dispatch` of type `app-release`, so the version on
the site stays current.

## Contributing to the docs

1. Edit or add a Markdown file under `content/en/` **and** `content/de/`
   (both languages are required).
2. If you add a page, register its slug and titles in `content/nav.json`.
3. Follow the conventions in [`tools/AUTHORING_BRIEF.md`](tools/AUTHORING_BRIEF.md).
4. Open a pull request.

Two details about the Markdown: admonitions are written `!!! note "Title"` with
a body indented by four spaces, and the `---` front matter splits on the first
colon, so a description may contain an unquoted colon.
